# M0.5-L4 — Debugging from Evidence and Directing a Bounded Modification

Lesson ID: `M0.5-L4`

Status: Completed with limited assistance on 2026-08-27; independent mastery not claimed

Estimated required learner time: 60–75 minutes

Primary capability: using failed evidence to isolate a defect, direct one bounded correction, and verify the fix without accepting unrelated changes

Applicable resume-level gate: none; this is foundational evidence for later SQL, Python, dashboard, automation, and applied-AI work

Prerequisite evidence: `evidence/LEARNER_CHECKPOINT_M0.5-C3.md`

## Scenario and user

An AI builder has delivered a small local finance-operations helper whose output fails one known-answer case even though other checks pass. Jeremy acts as the operator-builder: he uses the evidence to isolate the behavior at fault, directs or approves one narrow change, inspects the relevant logic in plain language, and verifies both the corrected case and unaffected behavior.

This lesson uses safe local practice code created for the lesson. It does not implement the Expense File Readiness Checker or begin the finance flagship.

## Why this matters

`M0.5-L3` established that plausible output and builder-authored tests can conceal a material defect. This lesson adds the next control: move from a failed check to a bounded diagnosis and correction without rewriting unrelated parts of the tool.

The same loop recurs later in SQL, Python/pandas, dashboards, automations, APIs, and agent tools:

1. observe the failed evidence;
2. narrow the responsible rule;
3. state the intended behavior;
4. direct one bounded change;
5. inspect the changed rule; and
6. rerun the failed case plus regression checks.

Jeremy is not expected to memorize Python syntax or write a program from a blank page. AI may create and change the safe practice code. Jeremy owns the diagnosis, intended result, scope boundary, targeted inspection, and verification decision.

## Learning objectives

By the checkpoint, Jeremy will be able to:

1. distinguish a symptom from the underlying rule that could cause it;
2. use a failed known-answer case or reconciliation to narrow the defect;
3. specify a bounded correction without authorizing unrelated refactoring;
4. ask AI to expose and explain only the relevant implementation section;
5. verify the corrected case and at least one unaffected behavior; and
6. explain one remaining limitation or failure mode.

## Teaching method

### Teach

Briefly teach the evidence-to-diagnosis loop and model it on one adjacent example. Emphasize that a failed output identifies a symptom; targeted inspection and controlled experiments narrow the responsible rule. Explain why rerunning only the failed case is insufficient when the change could create a regression.

### Practice

Use one coherent local finance-operations helper with a deliberately bounded defect. Jeremy reviews the failed evidence, identifies the likely rule, states the expected result, authorizes or directs one narrow change, and evaluates the resulting diff and rerun evidence. AI executes routine local code and test steps.

### Demonstrate

Use a genuinely different defect or rule with reduced scaffolding. Jeremy diagnoses from the evidence, limits the requested modification, selects a regression check, and makes the readiness decision. Do not assess command recall or raw Python interpretation.

## Learner deliverable

A concise debugging and bounded-modification record containing:

1. observed failure and deterministic evidence;
2. diagnosis separating symptom from suspected rule;
3. intended corrected behavior;
4. bounded change request and explicit non-goals;
5. targeted inspection of the changed rule in plain language;
6. corrected known-answer result plus regression evidence;
7. ready, revise, or reject decision; and
8. one limitation or remaining risk.

AI may organize the record after Jeremy makes or approves the substantive judgments. AI-written code and passing tests alone do not establish learner mastery.

## Verification boundary

- Preserve the failing case before changing code.
- Change only the smallest rule needed for the approved behavior.
- Inspect the actual diff and the relevant implementation fact.
- Rerun the failed case with an exact expected result.
- Run at least one regression check covering previously correct behavior.
- Confirm no unrelated file or behavior changed.
- Record the maximum substantive assistance honestly.
