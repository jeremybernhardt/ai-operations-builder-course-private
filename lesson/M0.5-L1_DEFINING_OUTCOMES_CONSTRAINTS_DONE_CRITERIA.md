## Scenario and user

A finance operations analyst receives a synthetic monthly expense file from department owners before management reporting begins. Duplicate transactions, missing departments, invalid dates, or unusable amounts could make a polished report materially wrong. The finance operations manager needs a small **Expense File Readiness Checker** that determines whether the file is ready for reporting and identifies records that require correction.

This is a bounded, work-practical specification exercise using synthetic data. It is not the future finance flagship and does not begin `M1`. This lesson defines the intended result before any implementation, plan, code, or interface is chosen.

## Why this matters

An AI builder can choose syntax and draft an implementation quickly, but it cannot know which business exceptions are acceptable unless the operator defines them. The operator remains responsible for the user, desired outcome, material boundaries, observable acceptance tests, and the evidence required to call the work done.

The decision supported here is: **Can the finance operations manager accept the monthly expense file into the reporting workflow, and if not, which records require correction?**

## Given context for the guided attempt

The input is a synthetic August 2026 CSV with these required columns:

- `transaction_id`;
- `expense_date`;
- `department`;
- `vendor`; and
- `amount_usd`.

For this exercise, the file is ready only when:

- all required columns are present and structurally readable;
- every `transaction_id` is present and unique;
- every date is valid and falls within August 2026;
- every department is one of `Operations`, `Sales`, `Finance`, or `People`;
- every vendor is present; and
- every amount is numeric and greater than zero because this file contains gross expense submissions, not credits or refunds.

The checker must report the input row count, valid row count, exception row count, total input amount, and a row-level exception list with reasons. Any exception makes the file not ready. The checker may inspect the supplied file but may not silently remove, correct, or overwrite records.

The stakeholder has supplied these business rules so Jeremy is not expected to invent finance policy. Jeremy is responsible for turning them into a precise build brief, identifying any remaining ambiguity, and defining observable evidence for acceptance.

## Terms for this lesson

- **Outcome:** the useful change in the user's situation or decision.
- **Implementation instruction:** a proposed way to produce the outcome, such as a language, framework, file format, or interface.
- **Constraint:** a boundary the solution must respect.
- **Non-goal:** related work explicitly excluded from the build.
- **Acceptance criterion:** an observable condition used to test required behavior.
- **Verification plan:** how evidence will be obtained and reconciled independently.
- **Done criterion:** the complete evidence threshold for stopping work and accepting the result.

## Verification rubric

The guided brief is ready for the later transfer check only when:

- the outcome describes the user's decision or capability rather than naming a technology;
- the trusted inputs and authority boundary are explicit;
- at least one material constraint and one non-goal prevent likely scope or safety errors;
- every acceptance criterion is observable as pass or fail;
- the verification plan includes evidence beyond the builder saying the work succeeded;
- the done criteria require the full acceptance and verification evidence; and
- the plausible-wrong case could pass a superficial visual or happy-path check.

Passing the software or producing polished prose is not sufficient evidence of learner capability.
