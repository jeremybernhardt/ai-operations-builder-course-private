## Scenario and user

An AI builder has received the approved Expense File Readiness Checker brief and proposed an implementation plan. The finance operations manager still needs the same reporting-readiness decision, but no implementation should begin until an operator confirms that the plan covers the brief, exposes material assumptions, stays within scope, and names sufficient evidence for later approval.

This is a plan-review lesson. The checker, dataset, tests, interface, and storage layer will not be implemented.

## Why this matters

A technically polished plan can still encode the wrong business rule, skip a control, or add infrastructure that the user never requested. The operator-builder's job is not to approve a plan because it sounds competent. It is to trace every proposed step to an approved requirement, surface decisions the plan is making on the stakeholder's behalf, reject unjustified scope, and define the evidence required before code can be trusted.

The decision supported in this lesson is: **Is the proposed build plan safe and complete enough to authorize implementation?**

## Learning objectives

By the checkpoint, Jeremy will be able to:

1. distinguish a requirement from an implementation choice and an assumption;
2. map proposed work to an approved brief and expose unmapped work or requirements;
3. challenge at least one unjustified architecture or scope choice;
4. separate necessary work from optional expansion;
5. identify a plan decision that could make plausible output materially wrong; and
6. state the evidence required before implementation approval.

## Terms for this lesson

- **Plan:** the proposed sequence of work before implementation begins.
- **Requirement traceability:** a visible link between each plan step and an approved requirement.
- **Assumption:** something treated as true even though the approved source has not settled it.
- **Architecture choice:** a decision about the technical structure, such as language, storage, or interface.
- **Scope expansion:** work added beyond the approved outcome, constraints, or non-goals.
- **Approval evidence:** observable results that must exist before the implementation can be accepted.

## Teaching method for this lesson

### Teach

Locate plan review between the approved build brief from `M0.5-L1` and the later implementation, diff, debugging, and bounded-change work. Explain requirement traceability, assumption ownership, scope control, and approval evidence directly. Demonstrate all four controls with a complete adjacent workplace example before asking Jeremy to review the expense plan.

### Practice

Use the expense-checker plan as one coherent pre-build approval meeting. Present the business context and consequence of each material decision, then record Jeremy's approve, revise, defer, or escalate decisions. Assemble the reviewed plan only after Jeremy makes or approves those decisions; do not turn the activity into a line-by-line file hunt.

### Demonstrate

After the guided plan is verified, present a genuinely different work scenario with reduced scaffolding. Assess whether Jeremy can identify a material assumption, challenge scope or architecture, and request independent approval evidence without repeating an answer just supplied during practice.

## Learner deliverable

A reviewed version of the AI plan that contains:

1. an approve, revise, or reject decision;
2. a requirement link for every retained plan step;
3. identified material assumptions and the owner who must resolve each one;
4. at least one challenged architecture or scope choice;
5. a necessary-now versus optional-later classification;
6. required revisions before implementation may begin; and
7. the deterministic and independent evidence required before implementation approval.

## Review rubric

The guided review is ready for the transfer check only when:

- every retained step has an approved purpose;
- material business-rule assumptions are not silently converted into code decisions;
- a technical preference is not mistaken for a stakeholder requirement;
- work that conflicts with a constraint or non-goal is removed or explicitly deferred;
- required work and optional expansion are visibly separated;
- proposed evidence includes known-answer outputs and independent reconciliation, not only builder-authored tests or a polished display; and
- the review identifies at least one way the planned implementation could produce convincing but materially wrong results.
