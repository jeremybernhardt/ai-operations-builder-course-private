## Proposed approach

Build a small Python/pandas command-line checker. A user will provide the August 2026 CSV path, and the checker will write a JSON result plus a human-readable HTML summary. Store each run in SQLite so the finance team can audit prior files and later connect the results to a dashboard.

## Proposed steps

### Step 1 — Create the checker project

Create a Python project with pandas, a command-line entry point, configuration for the allowed departments and reporting month, an output folder, and a SQLite database.

Claimed brief link: the checker must inspect the supplied synthetic file and produce a readiness result.

### Step 2 — Read and standardize the source

Read the CSV, convert column names to lowercase, trim whitespace from column names and text values, and preserve an in-memory copy of the original rows. Treat column names as case-insensitive so small formatting differences do not stop the run.

Claimed brief link: required columns must be present and the source must remain unchanged.

### Step 3 — Validate file structure

Check that all five required columns exist. If one is missing, return `Ready: No`, identify the missing field as a file-level exception, and skip row rules that depend on that field.

Claimed brief link: every required column must be present and structurally readable.

### Step 4 — Apply blocking row rules

For each row, check transaction ID, date, department, vendor, and amount. For a repeated transaction ID, retain the first occurrence as valid and mark only later occurrences as duplicate exceptions. A row is valid when it has no blocking exception.

Claimed brief link: blocking rules, valid and exception counts, and row-level reasons.

### Step 5 — Calculate the high-amount warning

Calculate the median from every positive numeric amount in the file, including rows that have a blocking problem in another field. Add a nonblocking warning when an amount is greater than three times that median.

Claimed brief link: the temporary high-amount warning must remain separate from readiness.

### Step 6 — Calculate controls and readiness

Report input row count, valid row count, exception row count, the sum of every parseable numeric input amount, all row-level blocking reasons, warnings, and `Ready: Yes` only when there are no blocking exceptions. Label the amount total as unapproved when the file is not ready.

Claimed brief link: required output, reconciled controls, and readiness decision.

### Step 7 — Produce reporting-ready outputs

Write the JSON result and HTML summary. Also write a cleaned CSV containing only valid rows so the reporting team can continue without waiting for corrections. Do not overwrite the source CSV.

Claimed brief link: the manager needs to know which rows are usable, and the source must remain unchanged.

### Step 8 — Save run history

Insert the file name, run time, readiness result, counts, totals, and exception details into SQLite. Retain the history for a future dashboard and trend analysis.

Claimed brief link: reruns should be inspectable and should not change the source.

### Step 9 — Test and document

Create automated tests for the clean, duplicate-ID, combined-error, missing-column, and high-amount fixtures named in the brief. Capture a passing test report, one manual reconciliation for the clean fixture, sample JSON and HTML output, and before/after source-file hashes.

Claimed brief link: acceptance criteria, verification plan, done criteria, and unchanged source.

## Assumptions made by this draft

1. Python/pandas and a command-line interface are acceptable for the user.
2. Required column names are case-insensitive and surrounding whitespace may be normalized in memory.
3. For duplicate transaction IDs, only occurrences after the first are invalid.
4. The warning median includes positive numeric amounts from rows blocked for another reason.
5. The raw numeric total is the sum of every parseable amount; nonnumeric values contribute nothing.
6. A cleaned valid-row export and persistent SQLite history are useful within the current scope.

## AI recommendation

Approve this plan and begin implementation. Python/pandas is a common fit for CSV validation, SQLite provides inexpensive auditability, and the cleaned export lets reporting continue while the finance team resolves exceptions.
