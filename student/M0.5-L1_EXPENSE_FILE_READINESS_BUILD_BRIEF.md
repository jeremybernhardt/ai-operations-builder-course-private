## User and decision

A finance operations manager needs to decide whether a synthetic August 2026 expense file can enter management reporting and, if not, which records require correction.

## Desired outcome

The manager receives an evidence-backed `Ready: Yes` or `Ready: No` result, reconciled control totals, row-level blocking exceptions, and clearly separate nonblocking warnings.

## Trusted input and business rules

The input is one synthetic CSV with these required columns:

- `transaction_id`;
- `expense_date`;
- `department`;
- `vendor`; and
- `amount_usd`.

The file is ready only when:

- every required column is present and structurally readable;
- every transaction ID is present and unique;
- every date is valid and falls within August 2026;
- every department is `Operations`, `Sales`, `Finance`, or `People`;
- every vendor is present; and
- every amount is numeric and greater than zero.

Any violation of these rules is a blocking exception and makes the file not ready.

## Temporary anomaly-warning rule

An otherwise valid expense greater than three times the median of all valid positive expenses in the file receives a nonblocking high-amount warning. The warning does not change the readiness result.

This temporary rule is an investigative signal, not proof that the expense is incorrect. It remains nonblocking until the business supplies an approved transaction-level limit and its authoritative source.

## Required output

- readiness result;
- input, valid, and exception row counts;
- raw numeric input amount total, clearly labeled as unapproved when any blocking exception exists;
- row-level blocking exceptions with every applicable reason; and
- a separate list of nonblocking warnings.

The checker must not silently remove, correct, or overwrite source records.

## Constraints and non-goals

- Use only the supplied synthetic expense file and approved business rules.
- Keep blocking exceptions visibly separate from nonblocking warnings.
- Do not build a management dashboard, budget analysis, approval workflow, or automated correction process.
- Do not decide whether an unusual but valid expense is legitimate.
- Do not choose a programming language, framework, or interface in this brief.

## Acceptance criteria

1. A clean known-answer file returns `Ready: Yes`, zero blocking exceptions, correct row counts, and a reconciled input total.
2. A file containing any missing required column, duplicate or missing transaction ID, invalid or out-of-period date, unapproved department, missing vendor, nonnumeric amount, or amount at or below zero returns `Ready: No` and identifies every affected row and reason available.
3. A file whose only unusual condition is a valid amount greater than three times the valid-file median remains `Ready: Yes` and reports a separate high-amount warning.
4. Counts and totals reconcile independently to the source file and the checker leaves the source unchanged.
5. A raw input total cannot be presented as an approved reporting total when blocking exceptions exist.

## Verification plan

Use separate known-answer fixtures for a clean file, a duplicate transaction ID, multiple simultaneous blocking errors, a missing required column, and a valid file with one high-amount warning. Reconcile row counts, exception counts, duplicate IDs, and amount totals independently against the fixture records. Confirm that rerunning the checker does not change the source file.

## Done criteria

The build is done only when every acceptance case passes; all control totals reconcile; blocking exceptions and warnings remain distinct; the source file is unchanged; and the known limitation of the temporary high-amount rule is documented.

## Plausible-looking but materially wrong result

The checker could report `Ready: Yes` and a convincing expense total while failing to disclose a duplicated transaction. The duplicate could overstate expenses even though the output looks polished and internally consistent.
